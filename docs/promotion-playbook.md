# LeanTTY 推广工作目录与执行规范

> 状态：跨版本推广执行手册；不是活动 TODO
>
> 更新日期：2026-08-21
>
> 上位规则：[`project-principles.md`](project-principles.md) 与
> [`roadmap.md`](roadmap.md)
>
> 唯一活动清单：[`next-work.md`](next-work.md)

本文档单独罗列 LeanTTY 需要考虑的推广工作、建议方法、交付物、证据和停止条件。
它是长期执行目录，不代表所有事项已获授权，也不维护 checkbox。

后续一次只选择一项推广工作：先完成本文要求的全网调研，再共同确认方案；只有已授权且
尚未完成的具体交付才进入 `next-work.md`。推广可以与产品开发并行，但不建立第二份活动工作表。

## 1. 通用边界

### 1.1 真实性与发布身份

- 只宣传对应精确版本已经完成的能力。本地源码、开发分支、测试 HAP、方案和 GitHub Release
  都不自动等于 AppGallery 用户已经可以获得。
- 性能、稳定性、安全性、兼容性和竞品比较只使用可复现证据；不使用“最快”、“最安全”、
  “完美兼容”等无边界结论。
- 不把 HSL 手工启动 `sshd`、动态 IP 和普通 SSH Host 路径宣传成 LeanTTY 自动发现、启动或管理 HSL。

### 1.2 信任、隐私与合规

- 推广不得向产品引入账号、广告 SDK、行为跟踪、主机上报、终端内容收集或云依赖。
- 优先使用 AppGallery 渠道链接报表、平台公开阅读/互动数据、GitHub 公开数据和用户主动反馈，
  不用应用内遥测交换推广归因。
- 不购买评分、下载、点赞或评论，不使用虚假用户、隐藏推广身份或制造假口碑。
- 录屏、截图、文章和反馈样本不得包含真实密码、私钥、API Key、代理凭据、公司主机、
  用户终端内容或可识别个人信息。

### 1.3 执行权限

- Agent 可以调研、编辑仓库文档、准备素材、生成本地草稿、校验链接和分析公开数据。
- AppGallery 登录、商店信息修改、文件上传和提审由维护者本人执行，具体边界以
  [`release-process.md`](release-process.md) 为准。
- 论坛、社区、媒体、邮件和付费投放等外部发布需要单独授权；平台要求本人原创或禁止 AI
  辅助时，Agent 只调研规则和客观事实，不起草、润色或代发内容。

## 2. 每一项工作的全网调研门禁

下文每一项建议都必须从“第一步（强制，全网调研）”开始。这不是搜几个关键词或只看官网，
也不要求不可能的“读完整个互联网”。合格的全网调研必须在当前日期覆盖以下视角，并把
信息缺口也当作结论：

1. **官方规则。** 查询平台官方文档、社区规范、素材规格、推广/外链/AI 内容规则、账号权限、
   审核与计费方式，记录页面和调研日期。
2. **当前搜索与需求。** 在通用搜索引擎、AppGallery、目标平台站内搜索和 GitHub 中查询用户
   实际使用的关键词、问题、现有结果和 LeanTTY 当前可发现性。
3. **同类案例。** 收集鸿蒙终端/SSH 应用、跨平台终端、开源开发者工具和 Agent 工作流内容的
   可观察做法，同时看成功样本、无反馈样本和负面反馈。
4. **受众真实讨论。** 查询当前问答、论坛、视频评论、issue 和评测，区分用户任务、口头兴趣、
   平台营销文案和真实阻断。
5. **正反证据。** 主动寻找渠道不匹配、规则冲突、受众过小、内容过度竞争、转化链路断裂和
   长期维护成本等反例。
6. **交叉验证。** 关键结论优先由至少一个官方来源和一个独立案例支持；只有产品官网自述时，
   必须标注尚未验证。
7. **形成调研记录。** 记录问题、关键词、来源、发布/更新日期、地区与版本、共识、冲突、
   未知内容、建议、停止条件和下一次失效复核日期。

没有找到足够证据时，正确结果是缩小试验、更换渠道或暂停，而不是由 Agent 用常识补全答案。

## 3. 建议执行顺序

| 阶段 | 项目 | 原因 |
| --- | --- | --- |
| A. 事实与定位 | P01–P04 | 先决定能诚实说什么、对谁说、用什么证明 |
| B. 转化基础 | P05–P10 | 保证用户搜到后看得懂、信得过并能正确安装 |
| C. 内容资产 | P11–P14 | 先建立可复现主内容，再按渠道重写 |
| D. 渠道分发 | P15–P22 | 每次只试一个渠道，先理解社区再发布 |
| E. 反馈与改进 | P23–P25 | 把公开反馈转为产品证据，不追虚荣指标 |
| F. 条件性扩展 | P26–P28 | 只在设备、合作方或经济证据成立后启动 |

P01–P10 是首轮公开推广前的基础，P11 是当前旗舰内容，P15 是优先官方渠道。每完成一项，
都先看证据，再授权下一项。

## 4. A 阶段：事实与定位

### P01 建立对外版本事实基线

- **目标：** 任何素材都能回答“这是哪个版本、现在能否安装、证据在哪里”。
- **第一步（强制，全网调研）：** 按第 2 节查询 AppGallery 当前商店状态、公开搜索结果、
  GitHub Release/标签和同类应用版本呈现方式；不从本地源码推断用户能力。
- **建议方法：** 为当前商店版、当前 GitHub 版和下一版建立 claim matrix，每条宣传语句
  对应发布事实或真机证据。
- **交付物：** 可公开能力清单、不可宣传清单、版本/链接/证据映射和待维护者确认项。
- **完成证据：** README、商店文案、截图、视频和文章中的所有功能/版本声明均可回溯。
- **停止条件：** AppGallery 状态未确认时可准备素材，但不公开只存在于未上架版本的能力。

### P02 调研目标受众、任务和搜索需求

- **目标：** 确定首批内容对谁有用、他们正在搜索什么，不假设“鸿蒙用户都需要终端”。
- **第一步（强制，全网调研）：** 按第 2 节搜索鸿蒙 PC、HSL/openEuler、SSH、Code Agent、
  Codex/OpenCode 和鸿蒙终端相关问题，对比开发者、运维人员、Agent 用户和普通尝鲜者。
- **建议方法：** 用“设备/执行环境/核心任务/阻断/已有替代/可验证结果”描述 2–3 个核心受众，
  不写空泛人口属性画像。
- **交付物：** 受众优先级、高频问题、搜索词组、不服务受众和渠道匹配表。
- **完成证据：** 每个优先受众都有当前公开讨论和一条 LeanTTY 已交付能力可以闭合的任务。
- **停止条件：** 只有媒体转述、营销文案或无法对应 LeanTTY 能力时，不设为首批受众。

### P03 冻结产品定位与消息体系

- **目标：** 在 README、AppGallery、文章、视频和社区中使用一致但不机械复制的产品表达。
- **第一步（强制，全网调研）：** 按第 2 节对比系统终端、TermNext、南瓜 SSH、跨平台 SSH
  工具和 Agent 终端的当前表达、用户反馈与信任成本；不以静态功能表判胜负。
- **建议方法：** 准备一句定位、三条核心价值、三条非目标、一份核心任务对比和一组渠道标题；
  重点是键盘场景的快速、清楚、可恢复和本地信任边界。
- **交付物：** messaging guide，包含可用语句、禁用语句、证据要求、不同受众入口和 FAQ。
- **完成证据：** 陌生读者能区分 LeanTTY、系统终端、HSL 和 Agent 的职责，且文案不承诺大而全。
- **停止条件：** 定位需要改变使命、信任边界或支持受众时，先修改产品原则。

### P04 建立可公开证据与素材基线

- **目标：** 素材来自真实产品路径，不为发文临时制作无法重现的演示。
- **第一步（强制，全网调研）：** 按第 2 节调研 AppGallery 当前素材规格、鸿蒙优秀应用展示方式、
  终端产品演示范式和隐私泄露反例，核对版本、尺寸、时长和文案限制。
- **建议方法：** 使用受控服务器、专用测试账号、伪主机名和无秘密数据，在物理 HarmonyOS PC
  上录制首次连接、键盘交互、搜索、分屏、单文件传输和 ProxyJump 等候选场景。
- **交付物：** 经秘密扫描的原始截图/录屏、场景脚本、版本/设备映射和可公开性能数据。
- **完成证据：** 每份素材能回溯精确版本、物理设备和场景，且手工复核与自动秘密扫描均通过。
- **停止条件：** 含测试入口、未发布功能或敏感数据的画面不得公开使用。

## 5. B 阶段：转化基础

### P05 更新 README 与 GitHub 可发现性

- **目标：** GitHub 访客在首屏理解产品价值、适用设备、安装入口、核心能力、边界和求助方式。
- **第一步（强制，全网调研）：** 按第 2 节核对 GitHub 当前 README、Topics、About、Release
  与搜索规则，并分析同类开源终端项目的首屏结构、下载路径和无效信息密度。
- **建议方法：** README 首屏依次说明定位、真实界面、当前商店状态/安装入口、核心任务、信任边界、
  支持范围和文档入口；配置准确 Topics、仓库描述和项目网站链接。
- **交付物：** 更新后的 README、About/Topics 建议、截图资源、最新 Release 入口和失效链接检查。
- **完成证据：** 新访客不读架构文档也能在一分钟内判断是否适合自己并找到正确安装/帮助路径。
- **停止条件：** 不把 README 扩展成完整用户手册，不在首屏展示构建者才需要的验证命令。

### P06 优化 AppGallery 商店信息

- **目标：** 搜索和详情页准确表达 LeanTTY，降低理解与安装决策成本。
- **第一步（强制，全网调研）：** 按第 2 节核对 AppGallery 当前名称、简述、详述、分类、标签、
  关键词、素材、隐私和审核规则，搜索同类应用的当前结果与用户常用词。
- **建议方法：** 围绕“鸿蒙 PC、实体键盘、SSH、远程终端”组织标题与描述；先写用户结果，
  再写必要能力和明确边界，不堆砌 SSH 术语或不可验证形容词。
- **交付物：** 商店字段逐项建议、字符数校验、关键词依据、素材映射和维护者操作清单。
- **完成证据：** 每个字段符合现行规则，商店可获取版本支持全部声明，隐私/权限描述与产品一致。
- **权限：** Agent 准备和复核；维护者本人登录、修改、保存或提交。

### P07 制作 AppGallery 截图组

- **目标：** 不读长文也能看懂产品定位和 3–5 条关键用户路径。
- **第一步（强制，全网调研）：** 按第 2 节核对最新截图数量、尺寸、设备框、文案、语言与审核规则，
  对比当前高质量鸿蒙 PC 应用和终端应用的截图叙事。
- **建议方法：** 按“打开即工作、可靠连接、键盘效率、必要文件交付、跳板/恢复”排序；每张只表达
  一个结果，使用真实产品截图与克制注释，不伪造 UI。
- **交付物：** 原图、最终图、文案、顺序、版本/设备来源、秘密扫描结果和商店预览检查表。
- **完成证据：** 缩略图下仍可理解，文字可读、无敏感信息，且每张对应当前商店能力。
- **停止条件：** 需要用未发布能力才能讲清价值时，先调整叙事，不借测试版截图补足。

### P08 制作短演示视频

- **目标：** 用真实操作证明 LeanTTY 能帮助用户完成一个核心任务。
- **第一步（强制，全网调研）：** 按第 2 节核对 AppGallery、Bilibili 和目标社交渠道的当前时长、
  画幅、字幕、音乐版权、封面和审核规则，并分析同类产品视频的前几秒留存方式。
- **建议方法：** 首版优先 30–60 秒“启动 → 连接 HSL/服务器 → 运行真实 TUI/Agent → 搜索或分屏”；
  同时保留无配乐字幕版和可裁剪竖/横版源文件。
- **交付物：** 分镜、录屏、字幕、旁白、封面、版权清单、精确版本说明和不同渠道导出文件。
- **完成证据：** 视频中的每一步可在物理机复现，没有加速掩盖等待、没有秘密、没有未实现承诺。
- **停止条件：** 平台规格或音乐/字体/素材授权不清楚时不发布，先替换为自有或明确授权资源。

### P09 建立分渠道下载入口与归因

- **目标：** 用户点击后直接进入官方安装路径，并能在不加入应用遥测的前提下比较渠道效果。
- **第一步（强制，全网调研）：** 按第 2 节核对华为“应用下载直达”当前资格、链接类型、二维码、
  报表字段、归因窗口、地区/设备限制和隐私规则，并比较普通商店链接的失败路径。
- **建议方法：** 为每个正式渠道生成独立命名链接；维护渠道、页面、内容版本、创建日期和用途映射；
  GitHub 与非华为设备保留诚实的兼容提示。
- **交付物：** 渠道链接表、二维码/图章、落地位置、测试记录、报表读取方法和失效复核周期。
- **完成证据：** 在目标设备上点击、拉起商店、应用详情和安装路径均正确，报表能区分渠道。
- **权限：** 需要账号的链接创建与报表查看由维护者执行，Agent 准备参数和核验清单。

### P10 评估独立产品页与搜索收录

- **目标：** 判断 README 和 AppGallery 之外是否需要一个长期可控、可被搜索的产品入口。
- **第一步（强制，全网调研）：** 按第 2 节检查 LeanTTY 当前搜索结果、GitHub Pages/静态站点能力、
  备案/域名/维护成本、同类产品页结构和搜索引擎收录现状。
- **建议方法：** 默认先让 README 和 AppGallery 成为权威入口；只有搜索、中文呈现、下载直达或
  多媒体展示确有缺口时，才建立无账号、无跟踪脚本的最小静态页。
- **交付物：** 建/不建结论、信息架构、域名与托管比较、隐私/维护成本和收录验证方案。
- **完成证据：** 新入口解决了已证明的发现或转化缺口，并且内容权威关系与更新责任清楚。
- **停止条件：** 仅为“看起来更正式”或会形成第二份过期产品文档时不建站。

## 6. C 阶段：内容资产

### P11 完成 HSL/openEuler + Code Agent 旗舰教程

- **目标：** 用一条真正有用、可复现的鸿蒙 PC 工作流自然介绍 LeanTTY，而不是写产品软文。
- **第一步（强制，全网调研）：** 按第 2 节复核华为 HSL/openEuler 当前官方能力与限制、目标 Agent
  最新安装/代理要求、`sshd` 行为、现有教程质量、常见失败和用户搜索问题。
- **建议方法：** 主线为“初始化 HSL → 安装 Agent → 手工启动 `sshd` → 查询动态 IP → 配置普通
  SSH Host → 用 LeanTTY 运行 Agent TUI”；所有命令在目标 PC 从零复现。
- **交付物：** 长文、命令清单、环境/版本表、失败排查、截图、短视频片段、秘密检查和下载入口。
- **完成证据：** 未参与写作的人按公开步骤可以完成；文章明确 LeanTTY、HSL、Agent 和代理的职责。
- **停止条件：** 关键步骤依赖内部 API、固定 HSL 地址、未公开软件、个人凭据或无法复现的偶然状态时不发布。

### P12 建立核心任务教程系列

- **目标：** 围绕真实任务持续形成可搜索内容，而不是按功能清单逐条发广告。
- **第一步（强制，全网调研）：** 每篇开始前按第 2 节重新研究该任务的搜索需求、官方标准、竞品/系统
  终端做法、常见错误和现有内容缺口；不能复用上一篇的调研代替。
- **建议方法：** 候选顺序为首次可信连接、密钥迁移、tmux/OSC 52、终端搜索、单文件交付、ProxyJump、
  SSH 排障和后续长任务提醒；每篇只解决一个完整结果。
- **交付物：** 选题调研、可复现文章、命令/截图、适用版本、非目标、更新日期和渠道改写建议。
- **完成证据：** 每篇从搜索问题进入，以可验证结果结束，产品只出现在确实承担任务的步骤中。
- **停止条件：** 只有功能介绍、没有独立用户价值，或现有高质量内容已完整解决且 LeanTTY 无新增价值时不写。

### P13 建立每版发布传播包

- **目标：** 每个公开版本都能用用户语言说明变化、适用人群、升级理由和已知边界。
- **第一步（强制，全网调研）：** 按第 2 节核对目标平台当前 Release/更新日志规则、同类项目发布表达、
  用户最关心的升级问题和上一版传播反馈。
- **建议方法：** 从 CHANGELOG 和发布证据生成“用户结果、演示、升级方式、兼容/非目标、问题入口”；
  GitHub Release 是版本权威，其他渠道只做不同长度的重写。
- **交付物：** GitHub Release 文案、AppGallery 更新说明、短帖、截图/动图和渠道链接映射。
- **完成证据：** 各渠道版本号、发布日期、能力和下载入口一致，没有把实现细节当用户收益。
- **停止条件：** AppGallery 版本尚不可获取时，不发布暗示商店用户已经升级的传播包。

### P14 建立 FAQ、排障与比较内容

- **目标：** 在用户提出问题前提供可信答案，减少安装后因边界不清产生的流失。
- **第一步（强制，全网调研）：** 按第 2 节收集当前搜索问题、issue、评论、系统终端/竞品比较、SSH/HSL
  常见失败和错误答案，优先研究反对使用 LeanTTY 的理由。
- **建议方法：** FAQ 按“适用设备、为什么不用系统终端、数据在哪里、连接失败、HSL 限制、文件传输边界、
  为什么不做大而全”组织；比较只覆盖同条件高频任务。
- **交付物：** FAQ、排障索引、比较方法、证据链接、已知限制和更新时间。
- **完成证据：** 每条答案有明确事实来源或产品证据，并指出用户下一步而不是只解释原因。
- **停止条件：** 未验证的竞品质量、下载量、隐私行为和平台行为不得写成确定事实。

## 7. D 阶段：渠道分发

### P15 华为官方编辑、开发者月刊与内容合作

- **建议方法：** 使用完整可复现步骤、环境表、错误恢复和更新时间；标题对应真实搜索问题，正文先解决问题，

- **交付物：** CSDN 专用版本、代码块/图片、摘要、标签、下载直达链接和更新计划。
- **完成证据：** 发布后检查收录、阅读完成信号、收藏/评论问题和渠道安装数据，不以单次浏览量判断成功。
- **停止条件：** 规则不允许当前链接/AI 辅助方式，或搜索结果已充分且无独特实践时不发布。

### P17 知乎问题与回答

- **交付物：** 问题选择报告、平台适配回答、图示、来源、披露说明和独立渠道链接。
- **完成证据：** 答案完整解决题目，评论能形成新问题或修正，而不是只有产品点击。
- **停止条件：** 没有合适问题、必须夸大经历或会构成垃圾广告时不发。

### P18 掘金技术实践文章

- **交付物：** 掘金专用文章、技术图、代码/数据出处、产品披露和更新入口。
- **完成证据：** 读者即使不安装 LeanTTY 也能获得可复用知识，产品露出与文章结论自然一致。
- **停止条件：** 只能写成版本新闻或缺少工程证据时，改用其他渠道。

### P19 V2EX 产品故事与反馈

## 8. E 阶段：反馈与改进

### P23 建立公开反馈、支持与问题分流

- **目标：** 让真实用户知道在哪里反馈，并把问题转成可判断的产品证据。

  核心任务、复现、期望/实际结果和已脱敏证据；安全问题走私密渠道。
- **交付物：** 反馈入口说明、bug/需求/兼容性模板、脱敏指南、分类和响应节奏。
- **完成证据：** 反馈能区分产品缺陷、平台限制、执行环境问题、使用问题和产品决策，不要求上传秘密。
- **停止条件：** 不为反馈建立账号系统、应用内遥测、公开终端日志或无人维护的新社区。

### P24 处理 AppGallery 评价与公开口碑

- **目标：** 对真实评价及时、克制、可验证地回应，并识别重复阻断。
- **第一步（强制，全网调研）：** 按第 2 节核对 AppGallery 当前评论回复、举报、展示和开发者规则，研究
  同类应用正负评价、有效回复和引战/索评反例。
- **建议方法：** 定期由维护者查看；感谢事实反馈，追问最小复现，指出已知边界和修复版本；把重复问题转入
  项目评估，不要求好评换功能，不与用户争论。
- **交付物：** 回复原则、常见回复事实库、需升级到 issue/安全渠道的条件和周期性摘要。
- **完成证据：** 每条开发者回复准确对应当前版本，重复问题形成明确产品结论或说明。
- **权限：** Agent 可分析和准备事实；维护者本人使用商店账号回复。

### P25 建立无应用遥测的推广度量与复盘

- **目标：** 判断哪些工作带来真实发现、安装、反馈和持续使用线索，而不是只看阅读量。
- **第一步（强制，全网调研）：** 按第 2 节核对 AppGallery 下载直达报表、GitHub API/Insights、各平台
  公开指标定义、归因偏差、隐私限制和独立开发者合理基线。
- **建议方法：** 指标分层：曝光、有效阅读/观看、商店点击、下载/安装、反馈、重复问题、贡献和版本采用；
  每项推广开始前写成功阈值和停止条件，结束后记录解释而非只抄数字。
- **交付物：** 渠道/内容/版本映射、基线、观察窗口、结果、偏差、定性反馈和继续/修改/停止结论。
- **完成证据：** 能说明某项推广改变了什么认知或行为，以及哪些结论不能从现有数据推出。
- **停止条件：** 指标需要应用内跟踪用户、设备、主机或终端行为时放弃该指标。

### P28 付费推广与官方增长工具

- **交付物：** 投放假设、预算、素材、受众、合规检查、归因方案、停止条件和复盘。
- **完成证据：** 在预设观察窗口内获得可解释的匹配安装或反馈，且获客成本和维护成本可接受。
- **停止条件：** 免费路径尚未跑通、无法可靠归因、需要加入跟踪 SDK、受众不精确或预算收益不可解释时不投。
