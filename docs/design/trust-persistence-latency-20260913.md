# 指纹持久化延迟：诊断与修复

状态：2026-09-13 维护者确认方案；实现及针对性软件、真机验证完成，正式 C3/C4 未通过。
执行入口仍为 [Next Work](../next-work.md)，本文件不是另一份 TODO。

## 结论

修复前，新指纹信任和删除被同步持久化阻塞约 2.6 秒，旧代清理占约 1.55–1.58 秒。
现已改为既有所有者内的串行异步提交，并分离确定旧代的清理。真机中，删除的处理中
输出约 2 ms 收到终端写入确认，最终结果从原包约 2565 ms 降到本轮约 1554 ms。
这是单组当前数据规模的对照，不是屏幕首帧或长期性能承诺。不改存储格式、信任合同、
xterm 或未归属于本轮的数据；安全持久化仍在连接放行之前。

## 边界与原因

预期：信任决定持久化成功后才能继续 SSH；等待期间不能让 UI 长时间无响应。
最后正确边界是已接受本次输入，首个明确耗时边界是本地同步持久化；文件投影及提交后的
SSH 认证不是本次主要耗时。`SessionViewModel` 拥有信任交互，`DurableStateManager`
拥有持久化与投影提交，`DurableAssetStore` 拥有 chunk、校验、指针和代际清理。

`removeOtherGenerations` 先枚举路径下的 alias，再逐项查询属性并同步删除旧 chunk。
这种调用数量随数据代数与 chunk 数增长；本次计时直接确认清理耗时，但没有逐 API
采样，不能声称某一个系统 IPC 或密码算法独占了全部时间。

[官方 Asset Store API](https://raw.githubusercontent.com/openharmony/docs/master/zh-cn/application-dev/reference/apis-asset-store-kit/js-apis-asset.md)
同时提供 Promise 形式的 `add/query/update/remove` 与同步形式。同步调用由应用主线程
路径发起；把动画放在同一阻塞路径前不能保证动画已绘制。官方文档及本次证据均不支持
将其定性为 Huawei 或 xterm 缺陷；没有找到与本场景吻合的上游问题记录。

## 已确认方案及准入

1. 在现有持久化所有者内，为指纹的完整“读—修改—提交”采用串行异步执行；使用已有
   官方 Promise API，不引入通用任务框架、额外数据库或缓存权威。队列必须覆盖读取，
   不能只串行最后的写入，否则双 Pane 的信任与删除可能丢失更新。
2. 保留“写 chunk → 回读校验 → 切换指针 → 文件投影 → 接受指纹”的安全顺序。
   异步期间保持 Session/Pane 代际校验，取消或销毁后不能让晚到完成事件继续连接。
3. 将旧代清理与提交成功分开处理，缩小为确定的旧代。不能简单用定时器延后现有
   `removeOtherGenerations(path, oldActiveGeneration)`：后续写入可能已经产生新代，
   旧闭包会误删新数据。清理必须与权威提交协调，失败可留待安全 GC，不能回滚已确认信任。
4. 用户提交后立即给出尚未成功的等待状态；长等待可显示 ASCII 动效。状态提示和动画只是
   反馈，不提前接受指纹或宣称删除成功。先验证异步后 UI 可处理帧，再决定动效形式。

方案已获维护者确认。将必要安全测试、最小真机对照
和候选影响作为一批交付：双 Pane 并发信任/删除、提交失败、清理失败、取消/销毁、重启
持久化及无提前信任，再用相同数据规模验证主线程等待与可见反馈。不要为了复现实测延迟
继续跑完整矩阵；如果修产品，按 R4 生成新候选。窗口反馈尚未复现，独立保留，不顺带改动。

## 实现与验证（2026-09-13）

`DurableStateManager` 为指纹的读取、修改、提交和文件投影提供一个串行队列，失败不
阻塞后续事务。`DurableAssetStore.writeAsync` 使用官方 Promise API，仍先写 chunk、
回读校验，再发布指针。后台 GC 加入同一队列，避免把未提交的新代误当垃圾；旧代清理
只匹配 namespace、chunk 类型、路径及确定 generation，失败不会撤销已提交的信任。
其他资产仍使用原来的同步路径，没有把本次修复扩成全局存储改造。

Session 等待时输出 `Saving host key...`，删除输出 `Updating known_hosts...`，不提前
显示成功。等待时禁止重复信任回答，保留 Ctrl-C；取消、销毁或新的提示使旧决定失效。
本地查询/删除阻止同一 Pane 重叠命令，并隔离晚到输出。没有新增动画计时器：本轮先
交付清楚的静态反馈和已验证可继续处理的事件链路；首次实际绘制耗时仍未测量。

针对实际 ArkTS 所有者的 29 项 host 回归通过，覆盖串行并发、无提前信任、读回损坏、
提交/投影/清理失败、精确旧代隔离、后台 GC、Ctrl-C、Pane 销毁、双 Pane 及晚到事件。
大数据用 fresh store 验证持久化读取；不是系统强杀瞬间的磁盘故障实验。
既有 ArkTS 202/202、Mosh owner 16/16 和 policy/ssh-flow 检查通过。编译警告仍为 47 条：
严格指纹变化只有两个既有同步 API 调用的行号移动，核对原日志后更新基线，未关闭检查。

同一 ARM64 PC 的零模型 SSH 对照通过：三条本地命令和一条受控远端命令均单次输入、
单次 Enter、零不匹配；连接、删除及清理通过。新信任的 `Saving` 输出在连接完成前约
1533 ms 得到写入确认，说明等待期间输出往返可以推进。不存在记录的删除约 364 ms，
不把小样本波动解释成回归或收益。测量只复用已有安全事件，没有新增产品采样或原始
正文/秘密日志落盘。

六项 SSH 真机检查通过：正常密码连接、Ctrl-C 后恢复、关闭隐藏提示所在 Pane 后恢复、
双 Pane 认证、最小化恢复、隐藏提示时停止进程后的清理；偏好设置保持不变，11 条普通
命令一次输入/Enter、零不匹配。这里的取消发生在认证提示，不冒充“真机上精确暂停
Asset Store 后取消”；后者由可控的所有者回归覆盖。文件传输共用信任路径的等待、
失败和晚到回调由实际调用方测试覆盖，本轮不重跑完整传输矩阵。
