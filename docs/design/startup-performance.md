## 用户问题与目标

用户在 HarmonyOS PC 上直接使用 LeanTTY 时，体感启动速度慢于多款其他应用。这个体感
需要转化为可重复的端到端指标，定位时间实际消耗在哪个边界，再选择最小优化；不能根据
代码表面上的同步调用、ArkWeb 体积或单次日志间隔直接判定根因。

本版本的启动性能目标是：

> **缩短从用户点击 LeanTTY 应用图标，到终端能够正确接收并显示第一个字母的时间。**

该结果同时要求应用已经可见、首个 Pane 的终端已经初始化、焦点已正确落到终端、ArkWeb
与 ArkTS Bridge 可以双向通信、本地命令行能够处理输入，并且首字母已经真实绘制。只提前
完成其中一个中间节点不算启动完成。

## 主指标

### 起点 T0

用户在 HarmonyOS 桌面或应用启动器中点击 LeanTTY 图标，系统接受这次启动意图的时刻。
自动化测量必须尽量使用设备侧同一单调时钟或系统 trace 对齐这个时刻；若只能使用外部注入
命令时间，必须记录其固定开销和误差，不能把主机到设备的传输延迟算成应用耗时后直接下结论。

### 终点 T5

向首个 Pane 输入一个普通 ASCII 字母后，该字符已经沿真实生产路径完成：

```text
物理键盘或等价系统键事件
  → ArkWeb/xterm 输入
  → WebMessage Bridge
  → SessionViewModel 本地命令行
  → Terminal Surface 回写
  → xterm paint
```

终点必须证明字符出现在正确 Pane、正确命令行位置且后续输入连续可用。仅记录按键事件到达、
Bridge ready、调用 `term.write` 或提示符出现在 DOM 中都不能替代最终绘制结果。

### 主要统计

- **冷启动主指标：** 进程不存在时的 `T5 - T0`，是 1.4 的首要优化对象。
- **温启动护栏：** 进程仍存在、应用从后台回到前台时的 `T5 - T0`，不得因冷启动优化明显退化。
- 基线和候选在同一设备、系统版本、窗口状态、签名角色、数据状态和启动入口下各采集至少
  20 个有效样本，报告 P50、P95、最小值、最大值和排除样本原因。
- 首次安装、旧数据迁移、系统升级后首次启动单独验证正确性和最坏情况，不混入日常冷启动
  分布，也不因低频而允许无响应或输入丢失。

具体改善阈值必须在 1.3 基线形成后共同确认。不能先写一个没有设备依据的毫秒目标，也不能
只用平均值掩盖长尾。

## 诊断分段

主指标不拆分，但诊断需要在同一时间轴记录以下节点：

| 节点 | 可观察结果 | 作用 |
| --- | --- | --- |
| T0 | 系统接受图标点击启动意图 | 用户等待起点 |
| T1 | `EntryAbility.onCreate` 开始 | 区分系统调度与应用初始化 |
| T2 | `pages/Index` 内容完成加载并首次可见 | 定位 Ability、持久状态与 ArkUI 页面成本 |
| T3 | 首个 Terminal Surface 的 ArkWeb 页面结束加载 | 定位 ArkWeb 资源加载成本 |
| T4 | xterm、renderer 与 Bridge ready，`ltty>` 已完成首次绘制 | 定位终端初始化与首屏成本 |
| T5 | 第一个字母经完整本地输入回路绘制 | 最终用户指标 |

节点记录必须低噪声、无终端内容、无主机、路径、凭据或密钥信息。诊断能力优先使用系统
trace；需要测试包标记时，必须编译期隔离并在 production 包中裁剪。

## 基线场景

1. **日常冷启动：** 已完成首次安装和迁移，保留正常窗口状态、OpenSSH config、
   `known_hosts` 与少量密钥；结束进程后从桌面图标启动。
2. **空数据冷启动：** 没有 Host 和用户密钥，用于识别持久资产数量相关成本，不作为唯一
   发布结论。
3. **有界资产扩展：** 使用不含真实秘密的受控数据，观察 Host、known-host 与密钥数量增长
   是否改变启动分布；不得复制真实私钥进入测试材料。
4. **温启动：** 进程保留、窗口进入后台后重新点击图标。
5. **同条件参照：** 在同一设备上对系统终端和少量轻量应用执行相同冷/温启动协议，只用于
   判断 LeanTTY 的相对体感和数量级，不把不同功能、框架应用之间的差值直接当作缺陷根因或
   发布门槛。

## 2026-08-17 物理机证据

测量对象是精确 `v1.3.0` 产品源（commit
`b089a9d218fd75765c176c9a60e7c1e1cf0b3d22`）加编译期临时探针生成的 test-signed
诊断 HAP。探针只记录阶段时间，不改变初始化顺序；首次字符由设备侧 `uinput` 注入，并且

冷启动均先结束 LeanTTY 进程，再从系统应用中心真实点击 LeanTTY 图标。截图已确认首屏最终
状态为 `ltty> a`，T4 到注入的设备侧等待均不超过 250 ms。T0 是设备侧在调用 `uitest`

`HAD-W24 6.1.0.135(SP11C00E100R13P3log)`）。日常状态 20 次冷启动结果如下：

| 区间 | P50 | P95 | 最小 | 最大 | 结论 |
| --- | ---: | ---: | ---: | ---: | --- |
| T0 → T5 | 2763 ms | 2811 ms | 2699 ms | 2815 ms | 当前用户等待基线 |
| T0 → T1 | 380 ms | 386 ms | 360 ms | 387 ms | 系统调度不是主导项 |
| T1 → T2 | 1478 ms | 1520 ms | 1428 ms | 1542 ms | Ability 同步初始化是主导阶段 |
| T2 → T3 | 613 ms | 622 ms | 570 ms | 622 ms | ArkWeb 页面加载是第二级成本 |

SSH 投影全量恢复约增加 592 ms，全局 Asset Store 垃圾清理约再增加 620 ms。Preferences、
key inspect、reconcile 与 key protect 合计远小于这两个阶段。

为验证因果关系，诊断构建分别临时跳过对应调用，各采集 3 次日常冷启动。它们只用于估算

| 诊断变量 | T0 → T5 P50 | P95 | 相对基线 P50 |
| --- | ---: | ---: | ---: |
| 保持 1.3 顺序 | 2763 ms | 2811 ms | — |
| 仅跳过全局 GC | 2139 ms | 2230 ms | -624 ms（-22.6%） |
| 仅跳过 SSH 投影恢复 | 2211 ms | 2272 ms | -552 ms（-20.0%） |
| 同时跳过两者 | 1572 ms | 1604 ms | -1191 ms（-43.1%） |

因此当前根因结论是：**日常冷启动在窗口和页面加载前同步执行了两次全量 Durable 维护：
SSH 投影物化与全局 Asset Store GC；二者合计增加约 1.19 秒，是 T0 → T5 的主导可优化
成本。** 独立及联合 A/B 结果与内部分段一致。ArkWeb 仍有约 0.61 秒成本，但不是第一优化
对象。

证据摘要保存在本机忽略目录
`build/verification/startup-performance-20260817-102846/summary.json`，其 SHA-256 为
`82bbe4ddd9d720fa48b5fd2f2706de6b7aa5a51f909911d71751e88e053cf20b`。该目录是开发

## 已确认的产品架构

两个诊断开关都破坏必要维护，不能直接转成实现。2026-08-17 共同确认的产品架构是：

1. **首次可交互前只做最小初始化。** `DurableStateManager.initialize` 只建立单一 Asset Store
   权威来源并读取迁移标志；SSH config、known_hosts、密钥投影、枚举、校验和保护均不阻塞
   `loadContent`。
2. **以真正绘制完成作为后台准备起点。** Web 端在首批终端输出或恢复快照写入完成并跨过一个
   完整绘制帧后发送一次 `interactiveReady`。这发生在 `ltty>` 已可见、焦点和真实输入回路已成立之后，
   不用窗口出现、Bridge ready 或定时器猜测用户可用状态。
3. **所有 SSH 依赖共用一个 Promise。** `SshEnvironment` 进程内 single-flight 异步恢复投影，
   再完成遗留迁移/密钥校验与保护；每个 Session 只在该 Promise 完成后加载自己的 `SshConfig`。
   用户若更快提交命令，命令显示一次准备状态并等待同一 Promise，不建立命令队列或第二套
   readiness 状态机。失败会释放 Promise，下一次命令可以真实重试。
4. **只放行明确纯本地命令。** 空输入、帮助、退出和 `scp` 迁移提示无需 SSH 环境；其他命令
   默认经过门禁。这样未来新增命令不会因为漏维护一份 SSH 命令列表而绕过投影准备。
5. **GC 与 SSH 准备分离。** 全局 GC 在应用进入后台时执行一次；失败只记录并在后续进程重试，
   不阻塞首字母，也不引入常驻后台、无限重试或新的缓存模型。
6. **暂不改 ArkWeb、renderer 与 Bridge 主链。** 唯一新增的桥接语义是上述绘制完成事件；
   renderer、焦点、输入回写和现有 SSH Transport/Session 均保持原路径。

1.4 日常冷启动候选门槛确认为 **P50 ≤ 1900 ms、P95 ≤ 2100 ms**。温启动非退化门槛定义为
同设备同协议下 P50/P95 不出现超过 10% 且超过 50 ms 的双重退化；相对应用参照不作为发布
门槛，因为不同框架和功能边界不能提供比精确 1.3 自身基线更可靠的因果判断。

## 当前代码中的已测边界

当前候选启动事件链及已测结论如下：

1. `EntryAbility.onCreate` 在 `loadContent` 前只完成 Durable 迁移标志、偏好、主题、窗口与
   ArkWeb 进程策略；不再恢复 SSH 投影、执行全局 GC、枚举或保护密钥。
2. `Index.aboutToAppear` 创建首个 Tab、Pane、Session 和 Terminal Surface，只把 Context 交给
   Session；不会在挂载 Web 前加载 SSH config。资产规模影响仍须用受控场景确认。
3. ArkWeb 加载打包的 xterm 与 addon，创建 WebGL renderer、fit、搜索、序列化、链接处理和
   Bridge；T2 → T3 约 0.61 秒、T3 → T4 约 0.15 秒。若 Durable 优化后它成为主导阶段，再
   细分资源解析、renderer、fit 和首帧；当前不先扩大范围。
4. 首字母经过 ArkWeb → ArkTS → 本地命令行 → ArkWeb 的完整回路候选 P50 为 76 ms；后台
   Asset 查询没有阻塞首字母。T4 当下立即提交 SSH 命令则复用同一准备 Promise 并正确恢复。

## 2026-08-17 启动窗口连续性收尾

1.3 为跨卸载重装保留窗口矩形，在 `loadContent` 完成后才读取主窗并依次执行移动和缩放。
启动性能缩短后，系统 Loading 仍先以自身矩形出现，随后主窗口再执行这组应用侧恢复，形成
短暂但明显的尺寸和位置跳变。跨卸载重装保留窗口几何不是核心产品要求，不能为它继续维护
第二套窗口状态和启动后补偿路径。

最终实现删除 Asset Store 中的窗口矩形、`windowRectChange` 监听、300 ms 写入防抖及
主窗口加载后的 `moveWindowTo`/`resize`，只在 `onWindowStageCreate` 调用 HarmonyOS
`setWindowRectAutoSave(true)`。系统窗口服务因此成为重启窗口几何的唯一权威来源；卸载会
按平台语义清除这项状态，应用不再额外跨安装保留。

物理 HAD-W32 上先让系统窗口记忆完成一次正常关闭，再用只存在于诊断构建中的 1.5 秒延迟

## 调查与决策规则

1. 先在未修改的精确 1.3 发布身份上复现并记录基线。
2. 再使用只增加时间节点、不改变初始化顺序的诊断包定位最大阶段。
3. 每次提出一个明确根因假设，并用最小实验验证；不同时延后多个任务、替换 renderer 和修改
   Bridge，以免无法判断收益来源。
4. 只有主指标或其已确认主导阶段出现可重复改善，且安全与正确性护栏不退化时，才保留方案。
5. 两个不同假设均无有效收益时重新检查测量和关键路径；第三种 workaround 前执行架构与
   产品价值复盘，不堆叠特殊分支。

## 硬约束与非目标

- 不以 splash、静态截图、空窗口、不可输入的 `ltty>` 或提前上报 ready 缩短数字。
- 不丢弃、缓存后静默吞掉或错误重放用户在启动边界输入的字符。
- 不延后会导致错误 Host、未完成主机信任、未保护密钥或旧持久状态覆盖新状态的必要工作。
- 不把真实凭据、终端内容、文件路径或用户资产数量写入性能日志或公开证据。
- 不增加常驻后台服务、开机自启、进程保活、启动守护进程或云端预热。
- 不增加用户可调的“快速启动模式”，也不并存两套初始化与持久化模型。
- 不为了性能数字默认禁用正确的 renderer、搜索、链接、输入安全或恢复能力；只有证据证明
  某项不需要位于首次输入前时，才讨论延后初始化。

## 验收

- 同条件基线和候选样本完整，P50/P95 与分段数据可追溯到确切提交、HAP、设备和系统版本。
- 达到基线后共同锁定的主指标改善门槛，冷启动长尾没有被平均值掩盖，温启动不明显退化。
- 首个字符不丢失、不重复、不错位；实体键盘、中英文 IME、焦点、窗口和首个 Pane 所有权正确。
- 正常配置、known_hosts、密钥、窗口状态、首次迁移和异常恢复行为保持原有安全与可靠性。
- 优化没有新增长期后台成本、第二套状态或明显维护复杂度；无效实验和临时诊断能力已删除或
  由正式包编译期裁剪。
- 最终在 production 候选上从真实桌面图标完成一次人工冷启动与首字母输入确认；安装或看到
  窗口不能替代该结果。
