# Host Key 新增/删除延迟复查

状态：最小优化及定向验证完成，待 PR 合入。执行入口为 [Next Work](../next-work.md)；
本轮不开展正式发布验收。

## 合同与初始边界

用户确认新 key 后，必须等待安全存储和运行时投影提交成功，才能放行当前连接。
删除只有在持久化与投影完成后才能报成功；后续新连接不能使用已经删除的信任。
等待期间界面仍可处理输入，失败必须可见，取消/销毁不能被晚到完成重新连接。
双 Pane 新增/删除不能丢更新或乱序，重启以持久化权威恢复。

既有 [09-13 修复](trust-persistence-latency-20260913.md) 已使用 Asset Store Promise API，
并把确定旧代的清理移出提交等待。因此“再改为后台执行”不是尚未实现的独立方案。
当前 `SessionViewModel` 拥有 pending/取消代际；`DurableStateManager` 的单队列覆盖
读、修改、提交和投影；`DurableAssetStore` 拥有不可变 chunk、回读校验及指针发布。
Rust 接收已经提交的投影路径与最终信任决定，匹配/删除规则仍在纯 Rust core。

最后已确认正确的代码边界是调用方 await 同一个串行提交、失败不放行连接。
当前现场首个慢边界尚待测量；不能用旧版 1.55 秒或自动化输入准备时间代替新实测。
首个假设：安全存储逐块写入及两次逐块读取仍占提交大头，界面线程已经能调度；竞争
假设是队列积压/GC、投影同步 I/O 或完成输出未及时刷新。

最小诊断：同一设备与当前数据规模，用现有 `-SshPrerequisiteProbe -DiagnosticHap`
做一次零模型新信任、远端命令、退出和删除。临时探针只记录队列、读取、纯转换、
chunk 写入、回读校验、指针发布、文件投影耗时及 50 ms 事件循环响应计数；不记录
正文、主机、指纹或凭据。构建后自动恢复源码，保留诊断源码与包哈希；日志仅保留
匹配的数值事件。证据目录 `build/verification/host-key-latency-20260923/`。

后续方案须以该证据为依据，保留现有存储格式、唯一权威及提交顺序，不用提前报成功
掩盖耗时。软件选择实际存储/Session 所有者的 durable-trust、ArkTS、SSH flow 与
policy 检查；真机仅受影响场景，模型请求为零。

## 主源约束

[OpenHarmony Asset API](https://raw.githubusercontent.com/openharmony/docs/master/zh-cn/application-dev/reference/apis-asset-store-kit/js-apis-asset.md)

50 ms 定时器分别运行 66/65 次，最大间隔 59/87 ms；这证明等待期间事件循环能推进，
不是屏幕首帧或无掉帧保证。新信任提交完成至 SSH connected 约 72 ms；不存在记录的
删除也需 978 ms 读取。主要耗时在安全存储，纯 native 匹配、队列、投影不是本样本主因。
`baseline/probe/result.json` 为诊断通过、零模型，原通知开关/屏幕策略及夹具清理通过。

下一有界假设：同一不可变 generation 内的独立块可最多四个同时提交/读取，减少串行
等待；不并发两个信任事务，不改格式、API 版本或存储权威。写入批必须全部 settle 后
才检查失败、清理或释放事务；仍完整回读/校验，再发布指针/投影。先证实原实现的并发
反例失败，再进行同规模真机对照；无明显收益则撤回，不叠加存储改造。

四块并发已实测并撤回：相同字节数下新增 3316 ms、删除 3376 ms，分别对比基线
3408/3339 ms，没有一致收益。其实现和专属测试仅保存在本地
`rejected-parallel.patch`，不进入产品；`parallel/probe/result.json` 与清理通过。

第二个有界候选只将新写入块从 768 调至 1024 字节。[官方新增参数表](https://raw.githubusercontent.com/openharmony/docs/master/zh-cn/application-dev/security/AssetStoreKit/asset-js-add.md)
明确 SECRET 长度为 1–1024 字节。已有版本 1 清单记录实际块数和总长度，读取不依赖
写入块大小；旧读者能读取新块，新读者能读取旧块，不需要迁移或兼容分支。原格式
writer 的容量反例先失败，改常量后通过；旧/new reader 与重启、失败、并发、取消
合同仍通过。旧大数据样本扩至 660 行以维持超过 15 块的原测试规模。
只继续测这一低复杂度候选；若收益不足，则按原则收束并向统筹说明残余等待。

同设备、同内容长度的对照完成：新信任 2806 ms、删除 2763 ms，分别降低约 17.7% 与
17.3%；新写入均为 11 块。首轮仍需读取原 768 字节旧代，新增读 970 ms、写 878 ms、
回读 704 ms；删除读取新代 831 ms、写 940 ms、回读 730 ms。事件循环最大间隔
67/71 ms，诊断和清理通过。证据 `capacity/timing-metadata.json`、`capacity/probe/result.json`。
保留仅单常量的容量修复，不保留并发实现。收益是当前约 10.7 KB 样本的局部改善，
不是消除等待：约 2.8 秒仍受安全存储多次调用限制。停止进一步存储改造，继续无探针
包及重启/删除后重连验证；不减少回读、不提前信任或返回删除成功。
