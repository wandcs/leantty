# LeanTTY 产品与技术原则

> 状态：项目基础规则；首次生效：2026-07-18；最近修订：2026-08-22

本文档定义 LeanTTY 的使命、愿景、产品边界、功能取舍和技术设计原则。它不是某个
版本的需求清单，而是需求、设计、实现、评审和重构共同遵循的长期规则。

当其他当前文档、历史方案或局部实现与本文冲突时，以本文为准。`docs/archive/` 中的材料只用于追溯，不能作为新增功能或复杂度的直接依据。

## 一、产品方向与定位

### 1.1 使命

**让开发者和运维人员能够把 HarmonyOS PC 当作可信赖的专业命令行工作设备。**

使命说明 LeanTTY 为什么存在，是比具体产品形态更长期的约束。LeanTTY 不以维护
某项实现、协议或项目本身为目的，而以目标用户能否在 HarmonyOS PC 上完成专业
命令行工作为判断起点。

### 1.2 产品承诺

**让拥有可用执行环境的开发者和运维人员，能够把 HarmonyOS PC 作为主要的命令行
工作设备，而不必仅仅因为终端能力不足继续依赖另一台电脑。**

产品承诺描述 LeanTTY 应为用户带来的结果。它不承诺替代另一台电脑的全部能力，
也不授权 LeanTTY 承担命令行工作以外的产品职责。

### 1.3 长期愿景

**LeanTTY 要成为 HarmonyOS PC 上简洁、高效、体验最好的 TTY 入口。**

当前产品形态是键盘优先、开箱即用的可靠远程终端，通过 SSH 连接远端执行环境。
“远程终端”是当前阶段定位，不是永久限定；TTY 才是长期产品身份。

LeanTTY 面向主要在办公场所或桌前使用键盘和大屏，通过开发机、服务器等执行环境
完成开发和运维工作的主流用户。执行环境既可能由用户完全控制，也可能属于公司并
受到网络和权限限制；产品不默认用户是企业用户，也不以覆盖所有企业接入方案为目标。

### 1.4 核心竞争力

- **可靠是底线。** 终端、连接、安全和状态不可靠时，其他价值均不成立。
- **简洁高效是差异化。** 用更少的概念、步骤、设置和干扰完成高频终端工作。
- **键盘优先是主要体验方式。** 它服务桌前的专业工作效率，不表示产品以移动场景
  为主要定位。
- **弱网能力属于可靠性。** 合盖、短暂离线和网络变化会发生在真实工作中，但
  LeanTTY 不以“移动终端”作为产品标签。
- **HarmonyOS 原生是体验要求。** 产品应自然遵循系统的窗口、键盘、剪贴板、主题
  和生命周期，而不是把其他平台的终端界面原样移植过来。

“鸿蒙 PC 的 Ghostty”表示对产品品质和设计哲学的参照，不表示复制 Ghostty 的
功能清单。LeanTTY 借鉴终端应当原生、快速、安静、可靠的理念，但不以功能丰富度、
设置数量或可扩展性作为竞争目标。

### 1.5 在执行环境中的角色

LeanTTY 是执行环境的入口，不负责建设执行环境：

- 当前通过 SSH 接入远端环境；Mosh 可作为长期连接方式，但不因长期方向自动进入
  当前路线图。
- Shell、tmux、vim、helix 和主流 Agent TUI 等工具运行在执行环境中；LeanTTY
  保证主流终端兼容和交互质量，不把这些工具集成为应用功能。
- 如果未来 HarmonyOS 提供系统级 Linux 子系统或同类标准能力，LeanTTY 可以成为
  它的 TTY 入口。
- LeanTTY 不自行实现或捆绑 Linux 兼容层、BusyBox 用户空间、包管理器或通用命令
  运行环境，也不为尚不存在的系统能力提前建设抽象层。

### 1.6 当前产品边界

- 只面向物理 ARM64 HarmonyOS PC 和键鼠场景。
- 当前只通过 SSH 连接远端环境，不提供应用自带的本地 shell 或 Linux 环境。
- 产品心智是终端；SSH 是当前接入执行环境的方式，不是长期产品身份。
- 办公场所和桌前使用是主场景；不为手机、竖屏或纯触控场景引入当前复杂度。
- 产品以开源、免费方式提供；有限维护资源优先投入主流标准和核心体验，不承诺覆盖
  所有厂商或企业的专有方案。
- 不以功能数量、设置数量或可扩展性作为产品竞争目标。

## 二、四项最高原则

原则按以下顺序处理冲突：

1. **用户信任不可交换。**
2. **可靠是底线。**
3. **简洁高效是默认选择。**
4. **易用只优化核心路径。**

### 2.1 用户信任

- LeanTTY 的核心终端路径不得依赖账号或厂商云服务。
- 除完成用户主动发起的连接和操作所必需外，主机信息、凭据、终端内容和使用数据
  默认不得离开设备。
- 任何便利、商业利益、统计或增长需求都不能削弱这一边界。
- 新的外部服务必须有明确、可解释的数据边界，不得成为核心路径的前置条件。
- 开源本身不能替代可信行为；实际的数据流、存储和控制权必须符合本原则。

### 2.2 可靠

- 终端输入、输出、尺寸、焦点和状态必须正确且可预测。
- 连接、认证、主机校验、取消、断线和重连必须有确定行为。
- Tab、Pane、Session 之间不得串状态、串输出或隐式共享所有权。
- 密钥、主机指纹、远端标题、剪贴板和 Bridge 必须有明确安全边界。
- 失败必须可观察、可理解、可恢复，不能表现为无响应。
- 涉及真实交互和生命周期的行为必须在目标鸿蒙 PC 上验证。

可靠性所必需的复杂度不能因追求代码短小而省略。

### 2.3 简洁高效

- 减少用户必须理解的概念、入口、模式和配置。
- 减少代码中的状态源、所有者、特殊分支和跨层协调。
- 同一任务保留一条清楚的主路径，不并存多套等价操作模型。
- 优先复用终端、连接和 HarmonyOS 标准，不自建平行的数据模型。
- 高频终端工作优先提供稳定、直接的键盘路径，避免不必要的模式切换和鼠标往返。
- 启动、连接、输入、输出和界面反馈应及时；性能工作以真实体验和测量证据为依据。
- 不为假想需求提前建设扩展点、插件层、通用框架或兼容层。
- 删除已经失去价值的功能和抽象，视为正常维护而不是功能倒退。

界面元素少并不自动等于简洁，快捷键多也不自动等于高效；如果隐藏界面或增加操作
模式导致状态更难理解，应优先保证可靠和清楚。

### 2.4 易用

- 打开应用后应尽快进入可工作的终端路径。
- 高频操作应直接、可发现，并具有稳定的键盘行为。
- 默认值应适合大多数用户，避免把必要决策转嫁给用户。
- 错误信息应说明发生了什么，以及用户下一步可以做什么。
- 低频高级需求优先由 `.ssh/config`、`known_hosts` 或远端工具解决。
- 不为少量用户或偶发体验增加永久入口、长期状态和维护负担。

## 三、功能取舍规则

任何新增功能、设置、交互模式或兼容逻辑，必须依次回答：

1. 它是否要求用户用数据、控制权或核心路径可用性交换产品能力？
2. 它是否直接服务“通过 TTY 进入执行环境并完成终端工作”的核心路径？
3. 不做它，目标用户是否会频繁受阻，而不仅是少一点方便？
4. 终端或连接标准、HarmonyOS 系统能力、执行环境或其中的工具是否已经能够解决？
5. 它会增加哪些永久概念、状态、入口、依赖和故障模式？
6. 删除它以后，产品是否仍然完整成立？
7. 它能否用更小、更局部、没有新概念的方式解决？

用户提出的现象或改动诉求首先授权调查其目标，不自动授权实施带有隐含代价的具体方案。
如果实现会改变终端或平台标准语义、削弱可靠性或兼容性、改变已发布契约、增加长期特殊
分支，或用一种体验交换另一种体验，必须先向维护者说明受益、代价、受影响场景、替代方案
和验证边界。只有在这些取舍讨论清楚并得到明确确认后才能实施；不能把“把这里改掉”解释
为对未说明代价的授权。没有上述实质取舍的常规、可逆实现仍按正常授权自主完成。

默认决策：

- 与用户信任原则冲突：不做。
- 核心路径上的正确性、安全性和可恢复性问题：必须做。
- 高频需求且能保持现有模型简单：可以做。
- 仅有假想用户、低频收益或需要长期架构负担：不做。
- 有价值但证据不足：记录问题，不提前实现。

不能只用“Ghostty 有”“以后可能扩展”“实现起来不难”作为加入功能的理由。

### 3.1 应长期做好的能力

- 当前阶段的 SSH 连接、认证、主机指纹、取消、断线和重连。
- 正确、流畅的终端输入输出，以及主流 Shell、tmux、编辑器和 Agent TUI 兼容。
- 键盘、焦点、复制、粘贴、搜索和窗口尺寸体验。
- 少量 Tab 和最多双 Pane 的清楚并行模型。
- 明确的连接状态、错误信息和恢复路径。
- 少量必要设置，例如字号、透明度和窗口状态；产品保持一套固定配色，不增加主题概念。
- 与 HarmonyOS PC 窗口、剪贴板、主题和生命周期的自然集成。

### 3.2 默认不进入产品范围的能力

- GUI 主机资产管理和自建主机数据库。
- SFTP 文件管理器、应用自带的本地 shell、包管理器或 Linux 环境模拟。
- 内置 AI 或 Agent 平台、协作、审计、堡垒机和共享会话平台；远端 Agent TUI
  的标准终端兼容不在此列。
- 插件系统、宏系统、脚本平台和为扩展而设计的公共框架。
- 无限分屏、复杂工作区布局和多套会话组织模型。
- 大量皮肤、主题以及低价值外观设置。
- 只为少数程序服务且维护成本高的终端协议扩展。
- 手机、竖屏和为非 PC 设备引入的响应式复杂度。

命令面板、自定义快捷键、会话恢复、多窗口等灰区能力，不自动进入路线图；只有出现明确、持续的核心场景证据后才重新评估。

## 四、技术原则

### 4.1 先明确所有权，再讨论分层

项目的核心领域模型固定为：

```text
App Shell
  └─ Tab → Pane → Session
                 ├─ SSH Transport (current)
                 ├─ Terminal Surface
                 └─ System Services
```

- Tab 拥有 Pane，Pane 通过稳定标识拥有一个 Session。
- Session 是连接生命周期和终端交互的业务边界。
- 不用数组相邻关系、当前索引、WebView 实例或 UI 状态隐式表达所有权。
- 每项可变状态必须有一个明确的唯一权威来源。

### 4.2 边界按职责存在

- **App Shell**：窗口、Tab、Pane、焦点和少量全局设置。
- **Session**：连接、认证、主机校验、断线、取消和重连状态机。
- **SSH Transport**：Rust/russh、PTY 和字节流，不决定 UI 文案或界面行为。
- **Terminal Surface**：ArkWeb/xterm 的显示、输入、选区和 resize，不管理业务状态。
- **System Services**：剪贴板、Preferences、窗口等 HarmonyOS 能力。
- **UI**：渲染状态并发送用户意图，不跨越边界编排多个底层对象。
- **Bridge**：只承载经过验证的协议消息，不承担业务规则或修补终端内容。

允许为保持这些真实边界而调整目录分层；`Page → ViewModel → Model → Common` 是依赖方向参考，不得凌驾于清楚的状态所有权之上。

该模型描述当前实现，不授权为 Mosh 或未来可能出现的系统级执行环境提前建立通用
传输框架。只有真实能力存在并通过功能取舍规则后，才按其实际生命周期扩展边界。

### 4.3 不为架构而架构

只有满足至少一项时才新增类型或抽象层：

- 拥有独立状态或生命周期。
- 封装明确且可测试的策略。
- 隔离真实的平台、进程或协议边界。
- 显著简化核心状态机或消除重复规则。

单一实现、没有替换需求的接口，纯转发的 Manager/Service，以及仅为缩短文件而进行的拆分，默认不增加。局部、直接、可测试的代码优于形式完整但需要跨文件追踪的架构。

### 4.4 控制复杂度的方向

- 业务规则与传输、渲染、平台适配分离。
- 结构化事件和状态优于由 UI 文案、字符串片段或时序猜测状态。
- 一个行为只有一个实现入口；不要在 ArkUI、WebView 和 Rust 三处分别修补同一规则。
- 优先删除特殊分支和重复状态，再考虑增加缓存、保留机制或补偿逻辑。
- 性能优化必须有测量证据，并且不能破坏正确性或明显增加维护复杂度。
- 新依赖必须解决明确问题；能够用平台能力或少量代码完成时不引入依赖。

### 4.5 验证是设计的一部分

- 自动化测试证明状态机、协议和纯逻辑。
- ARM64 构建证明目标平台代码能够集成。
- 真机验证证明焦点、键盘、剪贴板、窗口、持久化、终端交互和 SSH 生命周期。
- 编译通过不能替代行为验证，安装启动也不能替代交互验证。
- 修复应验证真实事件链，而不是只验证最终表象。

### 4.6 验收专用能力边界

- 为闭合 `next-work.md` 中明确的自动化或物理机门禁，可以在测试包中增加少量、明确
  标识的验收入口或触发逻辑。
- 验收能力必须复用待验证的生产事件链，只提供正常环境无法可靠触发的最小起点；不得
  建立第二套业务状态、持久化模型、模拟结果或长期调试面板。
- 验收入口和专用逻辑必须由编译期常量控制，并在正式包构建时执行分支裁剪；不能仅靠
  运行时隐藏、不可发现手势或发布前人工删除来隔离。
- 测试包必须有清楚标识，验收入口不得处理真实凭据、扩大数据权限或绕过产品安全边界。
- 每个入口都要对应具体门禁并有自动化约束；门禁消失或可由标准系统能力稳定触发时，
  应删除该入口。测试包证据不能替代正式候选的构建、签名和发布验证。

### 4.7 终端透明语义

- 透明度属于 LeanTTY 拥有的 Chrome 和内容承载表面。ArkWeb 与 xterm 默认背景以零 alpha
  透明透传，由各自区域的 ArkUI Surface 独占最终 alpha，不能再叠加 renderer 私有透明度。
- 终端的逻辑默认背景色与渲染 alpha 是两个独立语义。LeanTTY 只有一套固定配色，因此 xterm
  默认背景始终携带该配色的逻辑 RGB `#1E1E2E`，即使渲染 alpha 为零；透明度档位不得把
  OSC 11 等终端颜色查询退化为透明黑，也不得由潜伏代码分支派生第二套产品配色。
- renderer 判断默认背景与显式背景时只能读取背景颜色模式和颜色值。dim、italic、underline、
  overline、hyperlink、protected 等文字或扩展属性不得改变默认背景身份，也不得因为与颜色
  共用内部属性字而触发主题色背景矩形。
- 远端应用通过 ANSI、TrueColor 或其他终端序列显式设置的单元格背景，以及前景字形、光标
  和 selection，都是终端内容语义，默认保持上游 renderer 的不透明与颜色行为，不继承
  LeanTTY 承载表面的透明度。
- Transparency Off 必须真正关闭透明：Chrome、内容承载表面和显式终端内容均不保留隐藏
  alpha。不得通过识别 Unicode 块元素、Powerline 字形、应用名称或输出内容来猜测并修补背景。
- 未来若要让全部显式单元格背景透明、按颜色匹配透明或增加应用兼容特例，属于终端颜色
  语义与兼容契约变更。必须先提供主流终端行为、真实场景证据、颜色与可读性代价、维护成本
  和回退方案，并按功能取舍规则获得维护者明确确认后才能实现。
- 上游 renderer 缺陷确实破坏上述语义且版本升级不能及时采用时，可以在 vendored 资产生成
  边界保留一个最小本地补丁。补丁必须记录上游版本、提交和可读源码等价改动，锁定完整输入
  哈希与唯一命中并失败关闭，覆盖语义测试，明确删除条件；不得把压缩产物散落修改、应用识别、
  renderer fork 或长期兼容层作为默认方案。升级依赖时必须先判断上游是否已修复，再删除或重新
  审计该补丁，不能静默迁移。

### 4.8 终端 renderer 选择

- WebGL 是物理 ARM64 HarmonyOS PC 上终端的默认和优先 renderer。不得因为设备年龄、型号、
  User-Agent、远端应用名称、单个内容绘制缺陷或规避调试成本而主动选择 DOM，也不增加 renderer
  模式设置把实现取舍转嫁给用户。
- DOM renderer 保留为故障恢复，而不是兼容主路径：仅在 WebGL2 初始化失败、context loss，或
  目标真机证据证明当前 WebGL 路径无法可靠绘制且没有更局部可靠修复时使用。回退原因和实际
  renderer 必须可观察，恢复路径必须保持终端可用。
- 这项选择依据当前唯一支持的物理 ARM64 HarmonyOS PC 范围和真实能力证据，不承诺为范围外
  老旧设备建立永久分支。WebGL 可靠性仍须通过真机和 context-loss 恢复验证，不能把“现代设备”
  当作永不失败的假设并删除 DOM 故障回退。

## 五、变更治理

- 需求、方案和代码评审必须说明其如何符合本文原则。
- 引入新概念、长期状态、依赖或跨层路径时，必须说明为什么现有模型无法解决。
- 与本文冲突的需求不能通过局部实现静默落地；应先讨论并明确修改本文。
- 修改本文属于项目方向变更，应记录动机、替代方案和预期长期成本。
- 版本计划和旧愿景必须服从本文，不能用路线图倒逼原则让步。

### 5.1 战略调整

- 使命是最长期的方向约束；愿景、定位、产品边界和技术路径服务使命，不与使命并列。
- 当 HarmonyOS 系统能力、目标用户的工作方式、终端与执行环境生态或可用替代产品
  发生实质变化时，应从使命和产品承诺重新推导愿景与边界。
- 已有代码、技术投入、发布历史和维护项目本身都不能成为拒绝方向调整的理由。
- 环境尚未真实变化时，不以“未来可能”为理由提前扩张范围或建设抽象。
- 每次方向调整仍须记录证据、替代方案和长期成本，不能用使命为任意扩张背书。

### 5.2 存在条件与退出原则

- LeanTTY 的存在服务使命，不以项目持续存在或功能竞争为目的。
- 当市场上出现持续、可信赖、明显更好且大多数目标用户价格可负担的替代产品，
  并且 LeanTTY 已不再提供重要的独特价值时，应停止功能竞争并主动结束项目。
- 要求用户不必要地交出主机信息、凭据、终端内容、使用数据或核心控制权的产品，
  不属于可信赖的替代品。
- 明显过高的价格会阻碍使命实现；在缺少可负担替代品时，LeanTTY 作为开源免费
  选择仍有继续迭代的价值。
- 开源免费是保障可信与可获得的重要方式，不是要求项目无条件永久存在的目的。
- 项目退出不得静默遗弃仍在使用或分发的安全敏感产品，应清楚说明状态并为用户提供
  负责任的迁移路径。

### 5.3 2026-07-29 方向修订

- **动机：** 将使命、产品承诺、目标用户、核心竞争力和长期 TTY 身份写入顶层约束，
  避免把当前 SSH 实现或项目存续误认为最终目的。
- **采用方向：** 用户信任优先于其他产品利益；当前保持可靠远程终端定位，长期成为
  HarmonyOS PC 上简洁高效的 TTY 入口；可以接入标准执行环境，但不建设执行环境。
- **未采用方向：** 不定位为移动终端，不成为内置 Unix 工具的平台，也不把产品
  永久限制为 SSH 客户端；不为项目存续与更好、可信且可负担的替代品进行功能竞争。
- **长期成本：** 保留未来接入标准执行环境的空间，但不得为此提前增加抽象、依赖
  或路线图；坚持无账号、无厂商云依赖的核心路径会放弃部分便利能力；每种新入口和
  外部服务仍须独立通过本文的功能取舍、信任和验证规则。

### 5.4 2026-08-04 验收能力修订

- **动机：** 物理机上的 ArkWeb renderer、休眠、系统生命周期等关键失败无法总由外部
  HDC 权限稳定触发，缺少可控触发点会让真实生产恢复路径长期无法验收。
- **采用方向：** 允许测试包提供克制、门禁专用、编译期隔离的触发入口；入口只启动
  生产事件链，结果仍由真实状态、日志和物理机行为判定。
- **未采用方向：** 不把测试入口放入正式包，不增加通用开发者菜单、运行时秘密开关、
  模拟成功结果或与生产逻辑并行的测试实现。
- **长期成本：** 需要持续验证 release 分支裁剪和入口清理条件；换取关键生命周期门禁
  可重复、可审计的物理机证据。

### 5.5 2026-08-22 终端透明与 renderer 修订

- **动机：** 窗口透明暴露了 xterm WebGL 把非颜色属性误判为显式背景的问题；此前降低全部
  cell 背景 alpha 的补丁又破坏了 OpenCode 等 TUI 的颜色和块字形组合。局部表象修补无法同时
  保持透明合成、终端标准语义和长期可维护性。
- **采用方向：** 一套固定逻辑配色与窗口 alpha 分离；只透明默认背景，显式终端背景保持上游
  语义；以颜色位而非文字属性判断背景身份；WebGL 保持默认，DOM 只作可观察的故障恢复；必要
  的上游补丁集中在资产生成边界并对依赖升级失败关闭。
- **未采用方向：** 不升级到未发布的 xterm master，不提交本轮上游 PR，不识别 Codex/OpenCode、
  字形或输出内容，不按全部背景降低 alpha，不把 DOM 作为主动兼容模式，也不增加主题或 renderer
  设置。
- **长期成本：** 在上游修复或依赖升级前维护一个严格锁定的局部补丁，并持续覆盖 WebGL 真机
  语义与 DOM 回退；换取主流 TUI 在透明窗口中保持正确颜色、WebGL 性能路径和清楚升级边界。

最终判断标准：

> **LeanTTY 不追求成为功能最多的鸿蒙终端，而要让用户在 HarmonyOS PC 上始终拥有
> 一个可信、可靠、简洁高效、打开就能工作的 TTY。**
