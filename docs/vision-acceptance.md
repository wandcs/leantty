# LeanTTY 核心质量与愿景验收

> 状态：项目治理基线
>
> 更新日期：2026-08-03
>
> 上位规则：[`project-principles.md`](project-principles.md)
>
> 版本路线：[`roadmap.md`](roadmap.md)
>
> 当前执行：[`next-work.md`](next-work.md)

本文定义 LeanTTY 如何判断一个 milestone 是否保持了产品底线，以及如何判断使命、
产品承诺和长期愿景是否在当前阶段真实成立。它不是功能清单、版本计划或第二份 TODO。

文档职责固定为：

- `project-principles.md` 定义为什么存在、信任边界和长期取舍规则。
- `roadmap.md` 定义当前与后续 milestone 的用户结果、范围和进入条件。
- 本文定义跨 milestone 的核心质量门禁和产品结果验收。
- `next-work.md` 只维护当前已经授权的可执行工作。

## 一、两类验收不能混用

| 验收 | 回答的问题 | 频率 | 失败结果 |
| --- | --- | --- | --- |
| 核心质量门禁 | 当前候选是否仍然可信、可靠、正确且可发布 | 每个 release candidate | 不发布；当前修复进入 `next-work.md` |
| 愿景结果复盘 | 用户是否已能把 HarmonyOS PC 当作主要命令行设备，LeanTTY 是否仍提供独特价值 | 触发式、阶段性 | 调整 roadmap、保持维护或按退出原则行动 |

功能完成、自动化通过、ARM64 构建成功和应用能够安装启动，都不能单独替代其中任何一类
验收。核心质量通过也不自动证明愿景达成；愿景阶段性达成也不能免除后续版本的质量门禁。

## 二、每个 milestone 的核心质量门禁

每个发布候选都必须在其新增能力之外，保持以下长期底线：

1. **用户信任。** 核心路径不依赖账号或厂商云服务；主机、凭据、终端内容和使用数据
   不发生非必要外传；秘密不进入日志、历史、错误快照或非秘密持久状态。
2. **终端正确性。** 输入、输出、UTF-8、宽字符、PTY、resize、焦点、选择、复制粘贴和
   scrollback 正确；主流 Shell、tmux、编辑器和 Agent TUI 不因新增能力退化。
3. **连接与恢复。** 目标解析、主机校验、认证、取消、超时、断线、重连和错误恢复具有
   确定行为；合盖、后台、网络变化和 renderer 重建不会产生无响应、串流或伪成功。
4. **状态所有权。** `Tab → Pane → Session` 仍是唯一所有权模型；并行 Session 不串
   状态、输出、认证回答、主机信任、剪贴板和迟到事件。
5. **HarmonyOS 原生体验。** 物理键盘、窗口、剪贴板、主题、生命周期和系统快捷键在
   ARM64 HarmonyOS PC 上行为自然，不用其他平台假设代替真机结论。
6. **简洁与可恢复。** 高频路径没有新增不必要概念、重复入口和设置；错误说明发生了
   什么以及下一步；条件能力可以整体裁剪，不以更多特殊分支补救失败设计。
7. **发布证据。** 自动化证明逻辑和状态机，Rust 格式与 ARM64 构建证明目标集成，物理
   PC 证明交互和生命周期；需要发布时保留确切签名候选、版本、提交和验证连续性。

某个 milestone 没有修改其中一个领域，不表示可以跳过相应回归。验证深度应与变更风险
相称，但主机信任、认证、终端字节流、Session 隔离和秘密边界始终属于高风险底线。
各层证据具体证明什么以及何时必须使用真机，由
[`quality-strategy.md`](quality-strategy.md) 统一定义。

## 三、愿景阶段性达成标准

“把 roadmap 中的功能全部实现”既不是愿景达成的充分条件，也不是必要条件。只有以下
结果同时成立，才能判断愿景在当前产品与生态阶段已经达成：

1. **主要设备结果成立。** 拥有可用执行环境的目标用户能够持续把 HarmonyOS PC 作为
   主要命令行工作设备，不再仅因终端能力不足切换到另一台电脑。
2. **核心工作链完整。** 用户能够发现并进入执行环境，可信完成主机校验和认证，使用
   Shell、tmux、编辑器和 Agent TUI，诊断失败，并从断线、休眠和网络变化中恢复。
3. **长期可靠而非一次成功。** 结论来自真实工作周期和多次生命周期变化，不是单次
   happy path、演示、构建、安装或启动。
4. **简洁高效可感知。** 主流任务使用少量稳定概念和键盘路径完成；新增能力没有让
   Host、Identity、Session、配置和错误模型变得难以理解。
5. **可信与可获得。** 核心路径继续无账号、无厂商云依赖，数据和控制权边界清楚；
   开源免费仍使大多数目标用户能够获得可信选择。
6. **独特价值仍成立。** 与当时真实存在、可信且价格可负担的替代产品相比，LeanTTY
   在可靠性、简洁效率、HarmonyOS 原生体验或可获得性上仍提供重要价值。“最好”不按
   功能数量、设置数量或扩展性判断。

“阶段性达成”不是永久认证。HarmonyOS、执行环境生态、用户工作方式或替代产品发生
实质变化后，必须重新评估；不能用历史版本的结论替代当前证据。

## 四、愿景到 roadmap 的覆盖关系

下表用于发现“愿景有要求，但没有交付或证据路径”的空白。它不是版本完成表，也不把
条件 milestone 变成必须实现的承诺。

| 愿景结果 | 当前与拟议覆盖 | 仍然必须取得的结果证据 |
| --- | --- | --- |
| 主要命令行设备 | 1.0 建立可信 SSH TTY 基础；1.1 收敛认证、持久资产和工作连续性；后续 milestone 只解决持续出现的实际阻断 | 跨真实工作周期记录哪些任务已无需另一台电脑，哪些仍因终端限制被迫切换 |
| 发现并进入执行环境 | 当前直接地址和 OpenSSH Host；1.4 HSL 公开发现门禁失败后保留手工 Host 基线，不以私有接口构造专用入口 | 若未来系统开放稳定入口，目标用户无需维护第二套 Host/Identity，也能稳定找到并进入可用环境 |
| 可信连接与认证 | 1.0 主机校验、密码和私钥；1.1 标准多方法认证；1.5 条件跳板链；1.7 条件配置/信任互操作 | 主流受控环境的成功、拒绝、轮换、取消、秘密边界和并行 Session 证据 |
| Shell、tmux、编辑器和 Agent TUI | 1.0 终端基础；跨 milestone 永久终端回归；1.2 只补终端自身的高频检索缺口 | UTF-8、宽字符、PTY、resize、焦点、鼠标、剪贴板和高密度 TUI 的长期真实使用 |
| 断线、休眠和网络变化恢复 | 1.1 关闭现有生命周期门禁；1.6 只有 SSH 重连仍长期不足时才考虑 Mosh | 合盖、后台、锁屏、renderer 重建、网络丢失/切换和恢复后的内容及 Session 行为 |
| 必要文件到达执行环境 | 1.3 已交付受约束的 `put/get` 单文件传输；不扩展为文件管理器 | 最小能力持续在无覆盖、取消、失败和 Downloads 边界上可信，并在不需要时保持安静 |
| 简洁高效 | 固定 `Tab → Pane → Session`、统一命令体系和每个 milestone 的非目标/裁剪规则 | 高频任务步骤、错误恢复和概念数量在真实使用中保持清楚，不以功能数量替代效率 |
| 可信与可获得 | 无账号、无厂商云依赖、开源免费；隐私、安全和发布供应链基线跨版本适用 | 当前数据流、持久资产、日志、依赖、签名和分发继续符合公开边界 |
| 独特价值 | 不分配给某个版本；所有 roadmap 能力都必须服从退出原则 | 与当时可信、可负担替代产品的事实比较，以及目标用户仍选择 LeanTTY 的实际原因 |

如果某行的真实阻断已经由 HarmonyOS、OpenSSH、执行环境或可信替代产品解决，应裁剪
对应 milestone，而不是为保持表格完整继续实现。如果出现新的主要设备阻断，先通过
产品原则和本表定位缺口，再决定是否进入 roadmap；只有当前版本工作才能进入
`next-work.md`。

## 五、有效证据

愿景结果复盘至少应说明：

- 使用的确切 LeanTTY 版本/候选、提交、签名身份、物理 ARM64 HarmonyOS PC 和系统版本。
- 真实使用周期、执行环境和代表性工作负载，而不只列测试步骤。
- 覆盖的连接路径、认证方式、网络状态、Shell/tmux/编辑器/Agent TUI 和生命周期事件。
- 哪些场景已经能够只用 HarmonyOS PC 完成，哪些仍迫使用户换回另一台电脑，以及原因。
- 失败、裁剪、未覆盖环境和证据局限；不得把未验证候选写成已交付事实。
- 对当时可获得替代产品的事实性比较，以及 LeanTTY 仍有或已经失去的独特价值。

证据优先来自物理设备上的真实工作和可复现验证。用户反馈可以自愿收集，但不得为
愿景评估引入账号、强制遥测或上传终端内容；维护者自己的长期使用是有效证据，但不足以
单独证明所有目标用户的普遍结果。

以下内容不能单独证明愿景达成：功能数量、roadmap checkbox、代码量、下载量、构建
通过、安装启动、一次 SSH 成功、单一服务器兼容或与竞品功能表的静态对比。

## 六、触发时机

核心质量门禁适用于每个 release candidate。完整愿景结果复盘只在以下情况触发，避免
把持续治理变成每个版本的形式化负担：

1. 当前一轮已规划 milestone 已经完成、被证据正确裁剪或重新排序，需要决定下一轮
   roadmap 时。
2. HSL、Mosh 或其他新的执行环境入口/连接方式实际进入产品，显著改变主要工作路径时。
3. 真实使用持续出现“仍需另一台电脑”的终端阻断，或已有核心能力长期无人受益时。
4. HarmonyOS、SSH/Mosh、主流 TUI、目标用户工作方式或可信替代产品发生实质变化时。
5. 准备宣布进入稳定维护、重大方向调整或按项目退出原则结束时。

公开版本后的自然使用可以持续积累证据，但没有足够周期时应明确写“尚未评估”，不能
为了按时关闭 milestone 提前宣布愿景达成。

## 七、验收结论如何进入项目

愿景复盘只有四类有效结论：

| 结论 | 后续动作 |
| --- | --- |
| 尚未评估或证据不足 | 保持现状并说明需要什么证据，不提前增加功能 |
| 当前阶段未达成 | 将真实阻断重新通过产品原则；采用项进入 roadmap，当前项再进入 `next-work.md` |
| 当前阶段已达成 | 不继续功能竞赛；保持核心质量、兼容、安全和必要维护，等待新的真实触发 |
| 独特价值已经消失 | 按产品原则评估迁移、稳定维护或负责任退出，不以项目存续为目的扩张功能 |

条件 milestone 因证据不足而被取消，可以是正确的 roadmap 完成结果；愿景已经成立时，
不做低价值功能同样是成功。反过来，1.1–1.7 全部发布也不能绕过愿景结果证据。

## 八、文档维护

- 本文只维护稳定验收规则，不保存活动 checkbox、单次测试记录或各版本重复矩阵。
- 具体 milestone 的新增验收写入对应技术方案；当前可执行任务只写入 `next-work.md`。
- 阶段性愿景复盘只有确有长期战略价值时才形成带日期的历史记录；历史记录不授权工作。
- 修改本文的愿景判定、证据标准或结论类型属于项目治理变化，必须回到产品原则说明动机。
